# Componentes ESP-IDF
Para componentes de ESP Component Registry: añade `fabricante/componente` con versión fija en `src/idf_component.yml`, declara `componente` en `PRIV_REQUIRES` de `src/CMakeLists.txt` (`REQUIRES` sólo si lo exponen headers públicos), conserva `dependencies.lock`, ignora `managed_components/`, no uses `lib_deps` y valida con `pio run` (`pio run -t clean` antes si la resolución quedó obsoleta).

# Herramienta de configuración
En Windows crea el entorno con python -m venv tools\.venv y actívalo con .\tools\.venv\Scripts\Activate.ps1; en Linux usa python3 -m venv tools/.venv y source tools/.venv/bin/activate. Instala con python -m pip install -r tools/requirements-gui.txt y ejecuta la GUI con python tools/rover_gui/main.py. Para elegir el puerto diagnostica con python tools/rover_cli.py --port PUERTO_SERIAL probe --seconds 4 o calibra con python tools/rover_cli.py --port PUERTO_SERIAL calibrate; omitir --port conserva la autodetección de un único CH340. No abras dos clientes serie simultáneos; en Linux concede al usuario acceso al grupo propietario del dispositivo serie y vuelve a iniciar sesión.
La GUI configura NVS, muestra sensores, MAC propia, Wi-Fi y orientación 3D; la calibración usa el marco del rover X=-Xchip, Y=-Ychip, Z=Zchip y debe completar las seis caras antes de guardar. Valida cambios con pio run, pytest test/test_rover_gui.py y una prueba serial física a 115200 baudios.

# Sistema de visión
Configura en `.env` `VISION_CHALLENGE_REPO`, `VISION_HOST`, `VISION_PORT`, `VISION_CAMERA_INDEX` y `VISION_CAMERA_PROFILE_INDEX`; los índices empiezan en cero y el perfil se resuelve según los JSON de `vision/calibraciones` ordenados. Ejecuta `python tools/vision_client.py` para usar cámara real, iniciar `python -m vision.sistema --ventana` sólo si el puerto está libre y comparar la ventana de cámara con el mapa TCP; no uses `--synthetic` salvo que la prueba lo pida ni termines un servidor preexistente.
Para obtener datos para agentes ejecuta `python tools/vision_client.py --count N`; stdout contiene NDJSON, stderr diagnósticos y los códigos 0, 2 y 3 indican respectivamente contrato v3 válido, contrato incompatible y error de configuración o conexión. Conserva la lectura fragmentada por líneas, valida contra `contrato/schema.py` del clon y no programes con tramas rechazadas.

# Simulación de estrategias
Consulta tools/rover_sim/README.md para operar el simulador y tools/rover_sim/ESTRATEGIA.md sólo como historial de la estrategia; ningún resultado anterior demuestra el estado actual si su manifest.json no coincide con el código probado, y ante contradicción prevalecen el diagnóstico fechado más reciente de este archivo y una ejecución nueva. El simulador ejecuta los servicios C++ reales, sin placas, cámara ni servidor de visión. Requiere g++ con C++20, ESP-IDF de PlatformIO y VISION_CHALLENGE_REPO en .env. En Windows usa el Python preparado .pio/sim-venv/Scripts/python.exe; si falta, crea el entorno tools/.venv e instala tools/requirements-sim.txt. Desde la raíz ejecuta python tools/rover_sim.py --headless --scenario delivery --seconds 120 --output .pio/sim/NOMBRE_UNICO, sustituyendo python por el ejecutable del entorno. Sin --headless abre la GUI pausada; pulsa Iniciar. Inicia un proceso nuevo tras cambiar el firmware, pues una ventana abierta conserva su controlador anterior.
La entropía de motores representa una asimetría fija por ejecución, no ruido temporal ni una medición de par: escala el PWM efectivo izquierdo y derecho. parameters.motor_strength_difference admite de 0 a 1 y vale 0.04 por defecto; produce factores 1.02 y 0.98 centrados en uno, y la seed elige de forma reproducible e independiente de la entropía de visión cuál motor es más fuerte en cada rover. Configura el valor en el JSON o con --motor-strength-difference; usa 0 para desactivarlo y consulta manifest.json en realized.motor_strengths para conocer los factores aplicados. Los escenarios JSON antiguos que omitan parámetros nuevos heredan los valores predeterminados actuales; para reproducir la física anterior a ambas entropías especifica --no-vision-entropy --motor-strength-difference 0.
Modifica la estrategia en src/services, no una réplica Python ni la física para hacer pasar la prueba. Valida con pio run y python -m pytest test/test_rover_sim.py -q; comprueba entrega completa en delivery, crossing, vision-loss, peer-loss y delays. Exige tres entregas físicas, máscara combinada 7, ambos rovers terminados y detenidos, sin salidas de pista ni choques entre rovers u obstáculos durante toda la traza; verifica parada y recuperación ante pérdidas de entradas. Conserva cada ejecución en una carpeta distinta con scenario.json, manifest.json, trace.ndjson, report.json y registros C++; compara hashes con el código probado. Reproduce entradas con python tools/rover_sim.py --replay RUTA/trace.ndjson --output RUTA_NUEVA o repite el escenario con --config RUTA/scenario.json --headless --seconds 120 --output RUTA_NUEVA. Trata obstacles, blocked y edge como diagnósticos, no como entregas completas garantizadas; informa bloqueos y límites del modelo. La simulación no sustituye la validación física.

# Diagnóstico del pivote y navegación, 5 de octubre de 2026
El cuerpo mide 95 mm en su eje longitudinal y el eje motor está a 20 mm del borde trasero: su coordenada respecto al centro es menos 27,5 mm, no más 27,5 mm. Se corrigió el signo en tools/rover_sim/world.py y la descripción en tools/rover_sim/README.md; la prueba del pivote en test/test_rover_sim.py separa el cubo para medir el giro sin contacto. El centro del cuerpo ahora traza un arco de radio 27,5 mm al girar; cerca del borde inicial puede sacar una esquina de la pista.
La navegación C++ todavía presupone el centro como referencia de giro al estimar y seguir rutas, y la planificación no comprueba toda la envolvente barrida del chasis y los brazos. Por eso una rotación o corrección de rumbo desplaza el centro respecto a la ruta, dispara recuperación o salida de pista y bloquea entregas. Falta integrar la geometría del eje en odometría y control, planear maniobras con margen de giro y validar la envolvente completa y la recuperación con visión y comunicación interrumpidas; ninguna propuesta parcial de esos cambios quedó en el código.
Herramientas de verificación: PlatformIO pio run para el firmware, pytest test/test_rover_sim.py para la suite, y tools/rover_sim.py con headless, seconds 120 y output distinto por escenario. El 5 de octubre de 2026, tras añadir las entropías de visión y motores, pio run pasó y la suite actual registró 43 pruebas correctas y 7 fallidas: las cinco pruebas de entrega por escenario, seed42 sin completar y edge sin avance suficiente; las 5 pruebas específicas de entropía de motores pasaron. Las pruebas de entrega desactivan la entropía de visión pero conservan la diferencia de motores predeterminada 0.04.
Las métricas y archivos .pio/sim/pivot-sign-delivery-20261005, pivot-sign-crossing-20261005, pivot-baseline-final-vision-loss-20261005, pivot-baseline-final-peer-loss-20261005, pivot-baseline-final-delays-20261005 y pivot-baseline-final-pytest-20261005.txt son una referencia histórica anterior a las entropías, equivalente a vision_entropy=false y motor_strength_difference=0: delivery, crossing, vision-loss, peer-loss y delays lograron 0 de 3 entregas físicas y máscara combinada 0 en 120 s; registraron respectivamente 11660, 0, 11660, 11660 y 11635 cuadros con alguna parte fuera de pista, crossing terminó con un rover girando y no hubo choques entre rovers ni obstáculos. Sus manifest.json describen el código archivado y sus hashes ya no coinciden con world.py actual; no los presentes como validación del simulador vigente. Una compilación correcta y las pruebas aisladas no demuestran navegación funcional; la validación física sigue pendiente.

# Comandos para iniciar la simulación desde cero
En PowerShell, desde la raíz del proyecto, instala previamente g++ con C++20 y comprueba g++ --version; si el compilador no está en PATH, define $env:CXX con su ruta absoluta. Ten un clon de Vision-Rover-Challenge. Ejecuta if (-not (Test-Path .env)) { Copy-Item .env.example .env } y notepad .env; cambia VISION_CHALLENGE_REPO por la ruta absoluta del clon que contiene vision-system. No se necesita iniciar cámara, servidor de visión ni conectar placas.
En este equipo compila primero el firmware ESP32 e instala ESP-IDF con & "$env:USERPROFILE\.platformio\penv\Scripts\pio.exe" run. El entorno tools\.venv no contiene PlatformIO: no ejecutes allí python -m platformio salvo que instales el módulo con & .\tools\.venv\Scripts\python.exe -m pip install platformio. Si falta el ejecutable pio.exe del equipo, usa ese mismo pip install y luego & .\tools\.venv\Scripts\python.exe -m platformio run. El build de firmware debe terminar correctamente antes del build del controlador, que necesita cJSON de ESP-IDF.
Para el simulador en este equipo define $simPython = '.\.pio\sim-venv\Scripts\python.exe'; si falta ese entorno, ejecuta python -m venv tools\.venv, define $simPython = '.\tools\.venv\Scripts\python.exe' e instala & $simPython -m pip install -r tools\requirements-sim.txt. Compila el controlador C++ con & $simPython tools\rover_sim\build.py; también se compila automáticamente al arrancar tools\rover_sim.py y crea .pio\sim\rover_host con un hash en el nombre. Tras cambiar el firmware, inicia otro proceso de simulación para cargar el nuevo controlador.
Ejecuta una prueba con & $simPython tools\rover_sim.py --headless --scenario delivery --seconds 120 --output .pio/sim/delivery-INICIO_UNICO y reemplaza INICIO_UNICO por un nombre no usado. Para los cinco escenarios, ejecuta $runId = Get-Date -Format yyyyMMdd-HHmmss y luego foreach ($scenario in @('delivery','crossing','vision-loss','peer-loss','delays')) { & $simPython tools\rover_sim.py --headless --scenario $scenario --seconds 120 --output ".pio/sim/$runId-$scenario" }. Comprueba report.json, trace.ndjson, manifest.json y los registros C++ de cada carpeta; el código de salida cero del simulador no significa tres entregas. Ejecuta & $simPython -m pytest test/test_rover_sim.py -q para la suite.
Para ver la ventana, ejecuta & $simPython tools\rover_sim.py --output .pio/sim/GUI_INICIO_UNICO y pulsa Iniciar; la GUI no imprime en consola y normalmente mantiene el proceso abierto hasta cerrar la ventana. Para repetir un escenario conservado usa & $simPython tools\rover_sim.py --config RUTA\scenario.json --headless --seconds 120 --output RUTA_NUEVA; para reproducir sus entradas usa & $simPython tools\rover_sim.py --replay RUTA\trace.ndjson --output OTRA_RUTA_NUEVA. En Linux usa python3 -m venv tools/.venv, tools/.venv/bin/python para instalar y ejecutar, y pio run con g++ en PATH.
